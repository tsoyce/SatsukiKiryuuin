# XSatsu: концепция и дорожная карта

25 ноября 2026 · живая версия документа: https://claude.ai/artifact/FhUwaCiNy75eC8we916fBp

## Коротко

XSatsu вырастает из «редактора для одного Дня социолога» в **сервис персонализированной печати для кафедры и факультета**: шаблон + список людей → пачка готовых к печати файлов. Ядро для этого уже есть (PR #1): одна модель документа, вектор в PDF, ZIP, раскладка на листы. Не хватает серверной части: пользователей, общих проектов, базы данных и настроек.

Предлагаемый путь — пять фаз, каждая оставляет сайт рабочим:

1. **Фаза 0. Фундамент** — PR #1 в main, деплой Студии, тесты в CI, версия формата документа.
2. **Фаза 1. Сервер и MySQL** — PHP-API, конфигурация подключения, миграции, файлы ассетов отдельно от JSON.
3. **Фаза 2. Пользователи и проекты** — вход, роли, «мои / общие проекты», доступ по ссылке, корзина и версии.
4. **Фаза 3. Печать и производство** — мастер печати с профилями принтеров, серверная выгрузка больших тиражей, библиотека шаблонов.
5. **Фаза 4. Платформа** — мероприятия, приём данных из форм, проверка подлинности дипломов по QR, API.

Главное архитектурное решение: **остаёмся на PHP + MySQL + чистом JS без сборщика** (это совпадает с хостингом o.utmns.ru), но вводим чёткие слои и контракты, чтобы позже можно было подключить сборку или другой бэкенд без переписывания ядра.

## Концепция продукта

**Идея в одной фразе:** один макет + таблица людей = сотни именных документов, готовых к печати и рассылке, без дизайнера и типографии.

У Canva и Word-слияния эта задача решается плохо: нет векторного PDF-шаблона, нет обращения по полу, нет раскладки на SRA3 с метками реза, нет разделения слоёв струйник/лазер. Именно это и есть уникальная ценность XSatsu.

### Для кого

| Роль | Что делает | Что ей нужно от продукта |
| --- | --- | --- |
| Организатор (сотрудник кафедры) | Готовит приглашения и дипломы к событию | Вставить список из Excel, проверить, скачать ZIP или напечатать |
| Дизайнер / администратор шаблонов | Делает фирменные макеты | Загрузить PDF, расставить поля, закрепить фирменные элементы, опубликовать в библиотеку |
| Оператор печати | Печатает тираж на струйнике и лазернике | Профиль принтера, проходы, совмещение, повтор испорченных листов |
| Руководитель / администратор сайта | Управляет доступом | Пользователи, квоты, журнал, резервные копии |
| Получатель (гость, лауреат) | Получает документ | Скачать свой PDF по ссылке, проверить подлинность диплома по QR |

### Во что продукт может вырасти

Три горизонта, каждый опирается на предыдущий:

1. **Инструмент кафедры** (сейчас). Одна команда, несколько событий в год, печать на своих принтерах.
2. **Сервис для института / университета.** Несколько подразделений («пространства»), общая библиотека фирменных шаблонов ТюмГУ, единый стиль, журнал выданных дипломов и сертификатов.
3. **Платформа мероприятия.** Регистрация → список участников → приглашения → бейджи → дипломы → электронная рассылка и проверка по QR. Одна таблица людей питает все документы события.

Принципы, которые не меняются на всех горизонтах:

- **Печать — первична.** Результат измеряется в миллиметрах, текст в PDF остаётся текстом, фон — вектором.
- **Одно ядро.** Новый вид документа (бейдж, сертификат, табличка на стол) — это шаблон, а не новый редактор.
- **Работает без сервера.** Рендер и выгрузка остаются в браузере; сервер хранит, делит и проверяет, но не обязателен для печати.
- **Персональные данные — аккуратно.** ФИО, пол, места подпадают под 152-ФЗ: минимум собираем, краткий срок хранения, журнал доступа, сервер в РФ.

## Текущее состояние

Студия из PR #1 — это хорошее ядро примерно на 3200 строк JS (25 файлов), но целиком локальное. v25 была тремя отдельными редакторами, зато умела то, чего в Студии ещё нет.

| Область | v25 (legacy) | Студия (PR #1) | Что делать |
| --- | --- | --- | --- |
| Модель документа | Три разных формата | Один `xsatsu-doc` v1 | Зафиксировать JSON Schema и миграции версий |
| Рендер | Canvas-растр + pdf-lib | Одна сцена → canvas и векторный PDF | Добавить Web Worker для больших тиражей |
| Хранение | `api.php` + JSON-файлы в `invite-data/`, код проекта, ревизии, журнал | Только IndexedDB браузера + файл `.xsatsu.json` | MySQL + API, см. ниже |
| Ассеты (фоны, шрифты) | Внутри JSON | Внутри JSON как data:URL | Вынести в отдельные файлы по хэшу |
| Пользователи | Нет, только код проекта | Нет | Учётные записи и роли |
| Печать | Мастер: проходы, два принтера, профили, пакеты по 100 стр. | Раскладка, метки, слои, прямая печать | Перенести мастер на новое ядро |
| Тесты | Ручные чек-листы | `node tests/core.test.cjs` | CI в GitHub Actions + e2e на Playwright |
| Развёртывание | ZIP вручную на хостинг | Статика в корень сайта | Скрипт деплоя, релизы, откат |

### Технические долги, которые мешают двигаться дальше

- **Ассеты в data:URL.** Проект с PDF-фоном и двумя шрифтами весит 10–30 МБ, и этот объём перезаписывается при каждом автосохранении. Для сервера это неприемлемо: нужны ссылки вида `asset:sha256-…`.
- **Глобальный `window.XS`** и порядок `<script defer>` в `index.html`. Работает, но зависимости неявные; переход на ES-модули снимет проблему.
- **История полными снимками.** Для совместной работы и серверных версий понадобятся патчи (JSON Patch) или хотя бы ревизии с проверкой конфликта.
- **Нет версии API и контракта данных.** В v25 были добротные механизмы (проверка Origin, `expectedRevision`, лимиты, атомарная запись) — их стоит перенести в новый бэкенд как идеи, а не как код.

## Целевая архитектура

Ядро остаётся в браузере, сервер добавляет хранение, доступы и тяжёлую фоновую выгрузку. Так сохраняется работа без сети, а сервер остаётся простым PHP-приложением, которое живёт на текущем хостинге.

### Слои

| Слой | Где | Что внутри |
| --- | --- | --- |
| **Ядро (core)** | `app/js/core`, браузер + node | Модель, поля, вёрстка, сцена, рендер canvas/PDF, раскладка, ZIP. Без DOM и без сети. |
| **Хранилище (adapter)** | `app/js/store/*` | Один интерфейс `list / get / save / remove / putAsset`, две реализации: `LocalStore` (IndexedDB, как сейчас) и `RemoteStore` (HTTP API). Локальный кэш + очередь синхронизации. |
| **Интерфейс (ui)** | `app/js/ui` | Редактор, главная, вход, настройки, админка. |
| **API** | `server/public/api/` (PHP 8.4) | REST поверх JSON: `/auth`, `/projects`, `/assets`, `/templates`, `/exports`, `/admin`. Версия в пути: `/api/v1/…`. |
| **Сервисы** | `server/src/` | Авторизация, права, проекты и ревизии, ассеты, аудит, настройки. Без фреймворка или на Slim 4. |
| **Данные** | MariaDB 11.4 (MySQL-совместимая, уже стоит на сервере) + каталог `storage/` вне web-root | Таблицы пользователей и проектов; файлы ассетов — на диске по хэшу SHA-256. |
| **Фоновые задачи** | cron + `bin/worker.php` | Очистка корзины, резервные копии, серверная выгрузка больших ZIP (Фаза 3, через Node-скрипт на том же ядре). |

### Ключевые решения

- **Ассеты отдельно от документа.** В JSON проекта — только `{"src":"asset:sha256-ab12…"}`. Один и тот же PDF-фон хранится один раз на все копии проекта, сохранение весит килобайты. Файл `.xsatsu.json` для переноса остаётся самодостаточным (ассеты вкладываются при экспорте) или становится `.xsatsu` (ZIP: `doc.json` + `assets/`).
- **Оптимистичная блокировка.** Каждое сохранение несёт `revision`; сервер отвечает 409, если проект уже изменили. Это идея `expectedRevision` из v25. Совместное редактирование в реальном времени (CRDT, Yjs) — только если появится реальная потребность.
- **Таблица записей — часть документа, но с перспективой.** В Фазе 2 храним внутри JSON проекта. В Фазе 4 список людей становится самостоятельной сущностью «мероприятие → участники», и несколько документов ссылаются на него.
- **Никакого переписывания на фреймворк.** React/Vue не дадут печати ничего нового. Сборщик (Vite) имеет смысл только после перехода на ES-модули и для минификации (см. «Фронтенд»).

## MySQL, пользователи и проекты

MySQL хранит людей, права, метаданные и JSON проектов; большие файлы лежат на диске. Доступ строится по цепочке **пространство → проект → пользователь**: у каждого свои проекты, пространство (кафедра) даёт общие.

### Подключение к БД

Конфигурация — в `server/config/config.php` (не в git) или в переменных окружения; в репозитории только `config.example.php`. Переменные окружения всегда перекрывают файл.

```php
<?php
return [
  'app' => [
    'env' => getenv('XS_ENV') ?: 'production',   // production | staging | dev
    'public_origin' => 'https://o.utmns.ru',     // для проверки Origin, как в v25
    'secret' => getenv('XS_SECRET'),             // подпись сессий и ссылок, 32+ байта
  ],
  'db' => [
    'dsn' => 'mysql:host=127.0.0.1;port=3306;dbname=xsatsu;charset=utf8mb4',
    'user' => 'xsatsu_app',                      // отдельный пользователь: SELECT/INSERT/UPDATE/DELETE
    'password' => getenv('XS_DB_PASSWORD'),
    'options' => [PDO::ATTR_ERRMODE => PDO::ERRMODE_EXCEPTION, PDO::ATTR_EMULATE_PREPARES => false],
  ],
  'storage' => ['dir' => '/home/tsoy/xsatsu-storage', 'max_asset_mb' => 50, 'quota_mb_per_user' => 1024],
  'mail' => ['transport' => 'smtp', 'host' => '', 'from' => 'noreply@o.utmns.ru'],
  'auth' => ['session_hours' => 12, 'registration' => 'invite'], // open | invite | closed
];
```

Правила подключения:

- Два пользователя MySQL: `xsatsu_app` для сайта (без DDL) и `xsatsu_migrate` для миграций (запускается только из консоли).
- Только PDO с подготовленными запросами, `utf8mb4_unicode_ci`, время в UTC.
- База слушает только localhost; наружу порт 3306 не открываем.
- Миграции — нумерованные SQL-файлы + таблица `schema_migrations`; `php bin/migrate.php` применяет недостающие. Без Composer можно обойтись; с Composer — Phinx или Doctrine Migrations.
- Проверка здоровья: `GET /api/v1/health` отвечает версией схемы и доступностью БД и диска.

### Схема данных (первая версия)

| Таблица | Главные поля | Зачем |
| --- | --- | --- |
| `users` | id, email (уник.), name, password\_hash (argon2id), role (`admin`/`user`), status, created\_at, last\_login\_at | Учётные записи |
| `sessions` | id (случайный токен, хранится хэш), user\_id, expires\_at, ip, user\_agent | Вход через cookie `HttpOnly; Secure; SameSite=Lax` |
| `workspaces` | id, name, slug, settings JSON | Кафедра / подразделение |
| `workspace_members` | workspace\_id, user\_id, role (`owner`/`editor`/`viewer`) | Кто в команде |
| `projects` | id (ULID), workspace\_id NULL, owner\_id, title, kind, revision, doc JSON (LONGTEXT), thumb\_asset, rows\_count, updated\_at, deleted\_at | Проект и его текущая версия |
| `project_revisions` | project\_id, revision, doc JSON (сжатый), author\_id, created\_at, note | История версий, откат |
| `project_shares` | project\_id, user\_id или token\_hash, permission (`view`/`edit`), expires\_at | Доступ конкретному человеку или по ссылке |
| `assets` | sha256 (PK), mime, bytes, width, height, pages, created\_by | Файлы фонов, картинок, шрифтов |
| `project_assets` | project\_id, sha256 | Чтобы чистить неиспользуемые файлы |
| `templates` | id, workspace\_id NULL (общий), project\_id-источник, title, kind, published\_at | Библиотека шаблонов |
| `settings` | scope (`system`/`workspace`/`user`), scope\_id, key, value JSON | Настройки (см. следующий раздел) |
| `audit_log` | id, at, actor\_id, action, target\_type, target\_id, detail JSON, ip | Кто что и когда делал (как `activity` в v25) |

### Права

| Действие | Владелец проекта | Редактор | Зритель | Админ сайта |
| --- | --- | --- | --- | --- |
| Открыть, выгрузить PDF/ZIP | да | да | да | да |
| Править макет и записи | да | да | нет | да |
| Дать доступ, удалить | да | нет | нет | да |
| Опубликовать как шаблон | да (в своём пространстве) | нет | нет | да (в общие) |

### Переход с текущего хранения

1. При первом входе Студия предлагает «Перенести N проектов из этого браузера в аккаунт»: IndexedDB → API, ассеты вытаскиваются из data:URL и закачиваются по хэшу.
2. Серверные проекты v25 из `invite-data/` импортирует консольная команда `php bin/import-v25.php`, которая вызывает тот же `XS.Import` через node. Код проекта v25 становится ссылкой доступа.
3. Режим «без входа» остаётся: проекты живут в браузере, как сейчас. Админ может его выключить.

## Настройки

Настройки делятся на четыре уровня, и более узкий уровень перекрывает широкий: **сервер (файл) → сайт (админка) → пространство → пользователь → проект**. Секреты и доступ к БД меняются только в файле, никогда из интерфейса.

| Уровень | Где хранится | Кто меняет | Примеры |
| --- | --- | --- | --- |
| Серверные | `config.php` / env | Администратор сервера | Подключение к MySQL, `public_origin`, секрет, каталог хранилища, SMTP, уровень логов, лимит размера загрузки |
| Сайт | `settings` (scope=system) | Админ в интерфейсе | Регистрация (открыта / по приглашению / закрыта), разрешённые домены почты (`@utmn.ru`), квоты, срок хранения корзины и ревизий, режим «без входа», текст согласия на обработку ПДн |
| Пространство | `settings` (scope=workspace) | Владелец пространства | Фирменные цвета и шрифты, логотипы, подписанты по умолчанию (зав. кафедрой), профили принтеров, шаблон имени файла по умолчанию |
| Пользователь | `settings` (scope=user) | Сам пользователь | Тема, единицы (мм / пт), шаг привязки, принтер по умолчанию, язык, горячие клавиши |
| Проект | `doc.output`, `doc.settings` | Редактор проекта | Шаблон имени файлов и архива, формат и качество выгрузки, раскладка, метки реза, слои печати, правило обращения, язык переносов |

Реализация: один модуль `Settings` с описанием каждого ключа (тип, значение по умолчанию, допустимые уровни, кто может менять). Из этого описания строятся и проверка на сервере, и форма в интерфейсе, чтобы не дублировать код. Клиент получает уже сложенные значения одним запросом `GET /api/v1/settings/effective`.

## Функционал

Самый ценный ближайший функционал — то, что убирает ручную работу организатора: проверка списка, мастер печати, общие шаблоны. Приоритет: **P1** — делать в ближайшие фазы, **P2** — после сервера, **P3** — идеи на будущее.

| Функция | Зачем | Приоритет | Фаза |
| --- | --- | --- | --- |
| Мастер печати на новом ядре: проходы, два принтера, профили со смещением полей, тестовый лист совмещения | В v25 было, в Студии нет | P1 | 0–1 |
| Проверка списка перед выгрузкой: дубли, пустые поля, не поместившийся текст, опечатки в ФИО, неопределённый пол | Ошибка в дипломе = перепечатка | P1 | 1 |
| Импорт XLSX напрямую (не только вставка/CSV) и Google Таблицы по ссылке | Списки приходят в Excel | P1 | 1 |
| Серверное сохранение, «Мои / Общие / Доступные мне», корзина 30 дней, версии | Проекты не теряются при смене компьютера | P1 | 2 |
| Библиотека шаблонов с «замком»: фирменные элементы не двигаются, меняются только поля | Единый стиль, новичок не сломает макет | P1 | 2–3 |
| Персональные ссылки на скачивание и рассылка по e-mail («ваш диплом во вложении») | Электронные дипломы и приглашения | P2 | 3 |
| QR-код и страница проверки подлинности диплома (`/v/<код>`), реестр выданных | Доверие, учёт | P2 | 3 |

## Фронтенд, зависимости и оптимизация

Правило выбора библиотек: **берём готовое там, где задача общая** (разбор Excel, ZIP, QR, склонение, перетаскивание), **и держим своё там, где наша ценность** (модель документа, сцена, векторный PDF, раскладка). Каждая библиотека должна быть с свободной лицензией (MIT / Apache / BSD / OFL), лежать в `app/vendor/` с фиксированной версией и грузиться лениво, только когда нужна.

### Лучшие практики фронтенда

1. **ES-модули + import map вместо `window.XS`.** Сборщик не нужен: браузер грузит `import { build } from './core/scene.js'` напрямую. Node-тесты импортируют те же файлы. Vite подключаем позже только для минификации и хэшей в именах файлов.
2. **Типы без TypeScript-сборки:** `// @ts-check` + JSDoc + `tsc --noEmit --checkJs` в CI. Ловит ошибки модели документа, не меняя запуск.
3. **Однонаправленный поток данных** (уже есть `UI.edit()`): изменение → патч → история → автосохранение → перерисовка только изменившегося. Панели не меняют документ напрямую.
4. **Дизайн-токены в CSS** (`--xs-color-*`, `--xs-space-*`), светлая/тёмная тема, `@layer` для порядка стилей, стили по компонентам.
5. **Доступность:** все действия с клавиатуры, видимый фокус, `aria-*` на панелях, контраст WCAG AA, `<dialog>` для окон.
6. **Тексты интерфейса в одном файле** (`i18n/ru.js`) — задел на английский и единые формулировки ошибок.
7. **Безопасность:** Content-Security-Policy без `unsafe-inline`, никакого `innerHTML` с данными из таблицы, CSRF-токен для API, SRI для vendor.
8. **Тесты:** ядро — `node:test`; интерфейс — Playwright (создать → заполнить → выгрузить ZIP); визуальные — рендер PDF через pdf.js + pixelmatch против эталонов. Линтеры: ESLint + Prettier, PHPStan + PHP-CS-Fixer.
9. **Ошибки в проде:** самостоятельно размещённый GlitchTip/Sentry или хотя бы `POST /api/v1/client-errors` в лог.

### Оптимизация

| Что | Как | Эффект |
| --- | --- | --- |
| Выгрузка больших тиражей | Рендер PDF в Web Worker (ядро уже без DOM), шрифты и фон встраиваются один раз на весь тираж, прогресс и отмена | Интерфейс не замирает |

| Предпросмотр | Кэш растра фона и вёрстки текста по хэшу элемента, `requestAnimationFrame`, OffscreenCanvas | Плавное перетаскивание |
